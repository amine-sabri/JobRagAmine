# Interview notes

One section per phase: the decisions, the alternatives rejected and why, and the questions an
interviewer is likely to ask, with short answers. Written as the project goes, not afterwards.

## Phase 0 — reproducible skeleton

### Decisions

| Decision | Why | Alternative rejected |
| --- | --- | --- |
| A **separate** Postgres for the vectors | the index is rebuilt and dropped constantly; an HNSW build competes for shared buffers and I/O. Separation also lets the source role be read-only | adding `pgvector` to the JobCrusader database: couples an experiment to production data |
| **pgvector** rather than a dedicated vector store | metadata filters (city, contract, date), keyword search and vectors must meet in one query; Postgres gives `tsvector` + `pgvector` + SQL in a single engine, so hybrid retrieval needs no second datastore | FAISS (no metadata, no persistence, no text search), Chroma / Qdrant (a second service to run and keep in sync) |
| Postgres **16** for JobRAG, while the app runs 15 | different major version removes any temptation to point one at the other, and `pgvector/pgvector:pg16` is the maintained image | reusing the app's 15 |
| Port **55433**, bound to `127.0.0.1` | avoids the host Postgres (5432) and the JobCrusader dev container (55432); not reachable from the network | default 5432 |
| `.env` + `pydantic-settings`, DSNs masked by `mask_dsn()` | validation at startup instead of a `KeyError` in the middle of a 20-minute indexing run; one single place formats a credential for display | `os.environ` reads scattered over the modules |
| **venv + pip-tools**, two lock files | nothing to install on the machine, and `requirements.txt` pins transitive versions — `recall@5` cannot silently change because a dependency bumped a default | `uv` (not installed here), unpinned `requirements.txt` |
| `/health` returns **503** when degraded | a healthcheck, CI job or load balancer can act on the status code; a 200 saying `"status": "degraded"` is a lie to every automated caller | always 200 |
| One connection per call, **no pool yet** | there is no query path to make fast; a pool is added in phase 3 when `/search` makes latency measurable | premature pooling |
| Integration tests **marked and excluded by default** | `make test` stays runnable with no Docker; `make test-all` proves the real database setup | skipping DB tests entirely, or requiring Docker for every run |
| Results tables generated by `scripts/make_report.py` between HTML markers | a number nobody can re-produce is an anecdote. The command appears next to its output | typing the numbers into the README by hand |

### Verified, not assumed

`make test-all` → 15 passed. `/health` → 200 with the database up, **503** with the container
stopped (`OperationalError: connection refused`), 200 again after `make up`. Extensions actually
installed: `vector 0.8.7`, `unaccent 1.1`, `pg_trgm 1.6` on Postgres 16.16. `git check-ignore`
confirms `.env` and `data/offers.jsonl` cannot be committed.

### Questions an interviewer could ask

**"Why a second Postgres instead of just installing pgvector in the application database?"**
Blast radius and lifecycle. The index is rebuilt a dozen times during the experiments, and an HNSW
build competes for memory and I/O with production traffic. Separating them also allows the export
role to be strictly read-only, which turns "I cannot corrupt their data" into a property of the
system rather than a promise about my code.

**"Why pgvector rather than FAISS, Chroma or Qdrant?"**
Because retrieval here is not pure ANN: answers must be filterable by city, contract type and date,
and the hybrid stage needs keyword scores next to vector scores. In Postgres that is one query over
`pgvector` + `tsvector`, with no second service to synchronise. FAISS is faster at raw ANN but has
no metadata, no persistence and no text search, and at a few thousand offers ANN speed is not the
bottleneck — reranking is.

**"Your export only runs SELECT — why bother with a read-only role?"**
Because the guarantee should not depend on my code being correct. A bug, a copy-pasted script or a
dependency with database access can all issue a write. A role that *cannot* write makes the whole
class of accident impossible. Same reasoning as using a `NOT NULL` constraint instead of trusting
application-level validation.

**"What does `/health` actually check, and why 503?"**
Reachability, server version, and the presence of `pgvector` — a reachable database without the
extension would fail at index-build time, which is too late. It returns 503 in that case so a
Compose healthcheck, a CI step or a probe can act on the status code; the body carries the detail
for a human, with the password masked.

## Phase 1 — read-only export, cleaning, deduplication

### What the data actually looks like

The brief's column list was close but not exact: `Id` is a `uuid`, `Language` is an integer enum
(not text), and the table carries contact and CV-matching columns the export must leave behind.
Checked with `\d "JobOffers"` before writing any code. Measured facts that changed decisions:

| Fact | How it was measured | What it changed |
| --- | --- | --- |
| 63% of descriptions are truncated (Adzuna: 18,915 of 19,874 are *exactly* 500 chars, 19,719 end in an ellipsis) | `count(*) filter (where length("Description") = 500)` grouped by `Source` | the usable corpus is 9,089 full-text canonical offers, not 32,013; truncation is a flag, not a silent loss |
| `Language` 0 = French, 1 = English | stopword counts per value: 29,856/29,942 vs 2,026/2,071 | no guessing; `language_code` is derived, not invented |
| `ContractType` 0 exists (10,096 offers); 3 and 4 never occur; 7 (104) = euraxess + abg exactly | `group by "ContractType"`, cross-checked against `Source` | 0 is "non précisé"; the rest of the brief's enum is confirmed |
| `Status` and `Level` meanings unknown | `Status` 1 has mean `BestScore` 64 and 100% scored, `Status` 2 has mean 21 | kept as raw integers; nothing in the pipeline depends on a guessed label |
| Section headings in only 47% of full-text offers | regex for `^(missions?|profil|compétences?|…)` | phase 2 needs a size-based fallback, not just section splitting |

### Decisions

| Decision | Why | Alternative rejected |
| --- | --- | --- |
| Explicit 22-column allow-list, 11 columns excluded | `SELECT *` means a contact column added upstream silently enters the export. The allow-list fails closed | `select *` then dropping fields in Python |
| `ApplyEmail`, `ContactName`, `ApplyUrl` excluded — and `BestScore`, `BestCvProfileId` too | the first three are contact details; the last two are the platform's CV-matching scores, which describe the candidate, not the offer | exporting them "just in case" |
| Masking *before* every other transform | an e-mail must not survive because a later step reshaped the text around it | masking at indexing time |
| Keep duplicates, flag them with `duplicate_of` | a position posted in 82 cities is one job, but "in which cities?" is a real question; the canonical row keeps `duplicate_cities` | deleting copies, losing the cities |
| Union-find over two rules | the rules chain: A links x–y by text, B links y–z by title. Independent passes would produce two groups for one position | one rule only, or two independent groupings |
| Canonical = oldest row, id as tie-break | the choice must be identical across runs, or the index and the evaluation drift apart | first row seen (depends on `ORDER BY` and on luck) |
| Phone regex requires a *consistent* separator | without it, `02.190606-04` inside the ISO timestamp `2026-10-10T01:16:02.190606-04:00` was masked as a phone number. Re-running the export after the fix moved the count from 11 to 9: two of the eleven "phones" were timestamps | a looser regex, corrupting real text |
| Truncation detected on the *raw* description, before cleaning | whitespace normalisation can remove the trailing ellipsis that proves the cut | detecting it afterwards |
| `build_offer` lives in `src/jobrag/export.py`, not in the script | the privacy rules are the part that most needs tests; a function inside a CLI script is awkward to test | leaving it in `scripts/` |
| Committed sample is pseudonymised *and* self-checking | the script refuses to write a sample containing an e-mail, a phone number or a real company name (it caught two leaks: company names in titles, and company-owned URL hosts such as `protectic.fr`) | a hand-picked sample, trusted |

### Verified, not assumed

`make test-all` → **119 passed** (114 without a database). The read-only guarantee is a test:
`CREATE TABLE` raises `ReadOnlySqlTransaction`, `transaction_read_only` is `on`, and the role sees
exactly one table. The export of 32,013 offers takes **14 s** and masks 186 e-mails and 9 phone
numbers; 8,298 copies are flagged across 4,040 duplicate groups, the largest being one position at
MEGAGENCE posted in 82 cities.

### Questions an interviewer could ask

**"63% of your descriptions are truncated. Why not just drop them?"**
Because they still answer a whole class of questions: which company, which city, which contract
type, which salary, and the title itself. What they cannot support is "what does this offer
require?", so they are flagged rather than deleted, and the flag is what the generation step uses
to decide whether it may claim anything about requirements. Dropping them would also skew any
aggregation over the market ("how many CDI in Lille?") by two thirds of the data.

**"Why keep duplicates at all? Most pipelines deduplicate and move on."**
Because the duplicate *is* information here. One position posted in 82 cities is one job, so the
index must not return 82 chunks of the same text and crowd out everything else — but "where is
this job open?" is exactly what a candidate asks. Keeping the copies with `duplicate_of` lets
retrieval work on canonical rows while the canonical row still carries the 82 cities. It also
makes the deduplication auditable: I can read the largest groups and see whether the rules merged
things they should not have.

**"How do you know your masking works?"**
Three ways, none of which is "I read the regex". The export counts what it masked per offer, so
the total is visible on every run. The committed sample is validated by a script that refuses to
write if an e-mail or phone pattern survives — it caught real leaks the first time. And the unit
tests include the cases that *must not* be masked: ISO timestamps, SIRET numbers, salary ranges,
version numbers. That last group is where the bug was: the first regex masked part of a timestamp.

**"Your canonical row is the oldest. Does that matter?"**
It matters for reproducibility more than for quality: any deterministic rule would do, but a
non-deterministic one (first row returned by the database) would make the index, and therefore the
retrieval metrics, change between runs for no reason. Oldest-first also matches the intuition that
the first posting is the original and the re-posts are copies.

## Phase 2a — chunking

### Decisions

| Decision | Why | Alternative rejected |
| --- | --- | --- |
| Hard character budget, header and overlap included | e5-base truncates past 512 tokens **silently**: a 3,500-character offer would lose two thirds of itself with no error anywhere. A test asserts `n_chars <= max_chars` for every configuration | counting tokens at embedding time and hoping |
| Every chunk starts with `title · company · city · contract` | the chunk is what retrieval returns and what the LLM reads. "3 ans d'expérience exigés" is unusable without knowing which offer it belongs to, and citations become guesswork | storing the metadata only in the database and joining at display time |
| `non précisé` left out of the header | it was being stamped onto the chunks of 7,068 offers: noise in the embedding, and a token that would skew the BM25 scoring of phase 5 | including every field for consistency |
| Headings dropped from the chunk body | the label already carries the information; repeating "Missions :" wastes budget | keeping the heading line in the text |
| Section split, then paragraph, then sentence, then hard cut | only 47% of full-text offers have a usable heading (measured), so section splitting is an optimisation, not the mechanism | section splitting only — it would fail on half the corpus |
| A tiny last chunk is grown by taking atoms back from the previous one | a 40-character trailing chunk ("TR.") retrieves badly and reads worse | emitting it as-is, or dropping it and losing text |
| An empty description still yields one header-only chunk | the offer stays findable by title, company and city — exactly what a truncated offer can honestly answer | skipping the offer, making it invisible |
| Copies are not chunked (23,715 of 32,013 offers) | one position posted in 82 cities would otherwise occupy 82 slots in the top-k and crowd out everything else | chunking every row |

### The estimate was wrong, and why

I predicted ~36,000 chunks at `max_chars=1200, overlap=150`; the real figure is **51,321**. Two
mistakes: I reasoned from the *mean* description length instead of summing the real ones, and I
ignored the overhead — the header (~90 characters) plus the overlap (150) leave a real step of
~960 characters per window, not 1,050. Checked afterwards that section boundaries were not the
cause: raising `min_chars` from 200 to 600 only moves the total from 51,321 to 49,604.

| config | chunks | chars per chunk (p50 / p95) | chunks per offer (mean) |
| --- | --- | --- | --- |
| 1200 / 150 (chosen) | 51,321 | 749 / 1,175 | 2.2 |
| 1200 / 150, min 600 | 49,604 | 823 / 1,173 | 2.1 |
| 2000 / 200 | 38,348 | 742 / 1,891 | 1.6 |

The median chunk (749 characters) sits well under the budget because a third of all chunks come
from offers the source board truncated at 500 characters.

### Questions an interviewer could ask

**"Why not one vector per offer?"**
Two reasons. Anything past 512 tokens is silently dropped, so most of a 3,500-character offer would
never be indexed. And a single vector averaging missions, benefits and legal boilerplate matches
every query weakly — chunk-level retrieval returns the passage that actually answers, which is
also what makes a citation checkable.

**"Why put the title and company inside every chunk?"**
Because the chunk travels alone. Retrieval returns a passage and the prompt shows that passage; if
it only says "3 ans d'expérience exigés", neither the model nor the reader can attribute it. The
header also helps retrieval: a question naming a city or a contract type now matches text that is
really in the chunk, not only metadata sitting in another column.

**"Your chunks are 749 characters at the median but you configured 1,200. Is the configuration wrong?"**
No — the distribution is bimodal and the median sits in the lower mode: 33% of chunks come from
offers truncated at 500 characters by the source board, one short chunk each. Among full-text
offers the mean is 3.8 chunks of ~1,000 characters. It does mean the phase-5 comparison between
1,200 and 2,000 characters is really a comparison over the full-text half of the corpus, which is
worth saying out loud when I report it.

## Phase 2b — embeddings, and what the CPU actually does

### Measured throughput, and a wrong optimisation

| path | chunks/s |
| --- | --- |
| 16-chunk `encode()` calls, file order (first implementation) | 0.96 |
| 16-chunk calls, length-sorted input | 1.41 |
| one `encode()` call per 512-chunk window (shipped) | 1.75 |

Three lessons, in order of how wrong I was. First, I predicted 20–40 chunks/s on 4 CPU cores for a
278M-parameter model; the truth is **1–2.6 chunks/s** depending on chunk length, so the full corpus
is hours, not minutes. Second, I blamed padding waste and "fixed" it by sorting the whole corpus by
length — then measured a **0.97x** speedup, i.e. none, because my benchmark passed all 200 texts in
one `encode()` call and sentence-transformers already sorts internally. Third, the real problem was
my own batching: calling `encode()` with 16 chunks at a time prevents the library from doing that
internal sorting across a useful window. Handing it 512 chunks per call is **1.8x** faster, with
bit-identical embeddings (verified: `max |Δ| = 0.00e+00` between the two orders).

The embeddings being order-independent is what makes the run resumable without caveat: an
interrupted index can continue in a different order and the vectors are the same.

### Questions an interviewer could ask

**"Why not quantise the model or use a smaller one?"**
Both would work — int8 dynamic quantisation is typically 2–3x on CPU, and e5-small is ~2.4x — but
both change the embeddings, and the point of this project is to measure retrieval quality. I would
rather pay the CPU time once for the baseline and treat quantisation as a separate, measured
experiment than confound the first number I report.

**"You estimated 20–40 chunks/s and got 1.75. Does that matter?"**
It changed the plan: it turns re-indexing from a free operation into a multi-hour one, which is why
the phase-5 chunk-size comparison (1200/150 against 800/100 → 69,896 chunks) has to run on a subset
rather than the whole corpus. Getting the estimate wrong is cheap; not measuring before committing
to a design that assumes cheap re-indexing would not have been.

## Phase 4 — the labelling tool

### Decisions

| Decision | Why | Alternative rejected |
| --- | --- | --- |
| The labelling search is keyword + IDF, **not** the vector retriever | labelling from the system under test hides exactly the offers it fails to find: the ids I record would be the ids it already returns, and recall@5 would be flattered | reusing `/search` to propose candidates |
| It reads `data/offers.jsonl`, not the database | the questions can be written while the index is still building, and the tool needs no model | requiring the index |
| IDF weighting, after measuring the naive version | without it, "Kubernetes à Paris en CDI" ranked any Paris CDI title above the one offer mentioning Kubernetes: two common words in a title beat one rare word in a body | plain term counting |
| A term given as a filter is removed from the text score | `city:Paris` plus "Paris" in the text scored Paris twice and drowned the content word | leaving the text untouched |
| The file is rewritten after every question | labelling 100 questions is long and interruptible; losing an hour of work to a Ctrl-C would be unforgivable | saving on exit |
| Only canonical offers are proposed | a copy is never "the" answer — its canonical row is, and that row carries the other cities | labelling against all 32,013 rows |
| `type` is guessed and confirmed, never inferred silently | the target mix (30 fact / 25 filter / 15 aggregation / 15 offer / 15 none) only holds if the type is right, and only Amine knows what he meant | automatic classification |
| "none" questions are a first-class type, validated | the refusal rate of phase 7 needs questions with **no** answer; the schema refuses a "none" question that has relevant ids, and any other type without them | treating them as a comment |
